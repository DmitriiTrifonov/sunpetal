# Диалог на ARM: разведка (K-174, шаг 164.1 пилота)

Основание: `docs/native-script-dispatch.csv`, сгенерированный C (`generated/recomp/p_arm9_012.c`, `p_arm9_013.c`). Рабочий документ, дополняется по ходу шага.

## 1. Обработчики шага сценария: тонкие (статически)

Команды диалога вызываются из шага `0x02045BC4`; сами они почти ничего не делают, а ставят флаги состояния:

| Команда (код) | Обработчик | Что делает |
|---|---|---|
| `<TEXT_EX>` (54) | `0x02049234` (19 строк) | берёт параметр команды (`*(*(0x0207596C+0x1C)+8)` = ID реплики) → `*(0x020759EC+0x3C)`; пишет `*(0x0207596C+0x48)=1`, `*(0x0207596C+0x4C)=0`, `*(0x020758EC+2)=0`, `*(0x020758EC+0x74)=1`; ставит метку скрипта `*0x0206577C = 0x14` (состояние «текст») |
| `<SHOWWINDOW>` (75) | `0x02049D14` | `*0x02078598 = 1` |
| `<HIDEWINDOW>` (74) | `0x02049D08` | `*0x02078598 = 0` |
| `<NEXTPAGE>` (4) | `0x02048064` | пустая (`bx lr`) |
| `<WAIT>` (9) | `0x02048078` | 18 строк, вызывает `0x020532B0` |
| `<SETFACE2>` (53) | `0x02049178` | 87 строк, `0x020245B0` (поиск персонажа), `0x0204DC34`, `0x0204DC6C` |
| `<WINK>` (105) | `0x0204A4FC` | 33 строки, `0x020245B0`, `0x02029260` |
| `<CHOICE>` (25) | `0x0204824C` | 2 строки |

Вывод: диалог — конечный автомат вне обработчиков; `TEXT_EX` только запускает его (состояние `0x14` в `0x0206577C`, ID реплики в `0x020759EC+0x3C`). Сам разбор страницы, вывод букв и ожидание нажатия идут в коде, читающем эти поля (`0x020758EC…`, `0x020759EC…`: 187+111 упоминаний в `p_arm9_012.c`, 67+31 в `p_arm9_013.c`). Это предстоит развести динамикой (следующий пункт).

## 2. Динамика: что читает и пишет поля диалога

Адреса состояния окна уже известны рантайму (`crates/sunpetal-runtime/src/dialogue.rs`, лог реплик): `0x02075A28` — указатель на показываемый текст (0, если окна нет), `0x02075A20` — слово «в окне лицо» (ставит `SETFACE2`), `0x02075AFC` — писатель (шрифт), таблица загруженных реплик сцены `0x02074BEC` (счётчик `0x020740A0`, загрузчик строки `0x0204253C`). Опкоды в памяти: `SETFACE2` 0x35, `TEXT_EX` 0x36.

Трассы (`--repl`: `goto C01_01`, `watchw ADDR 4 CAP r`, 60 раз `press A 2` + `run 18`, `writes`; `goto` останавливается на начале сцены, без нажатий A реплика не наступает). Поле `fn` в `writes` — последняя вошедшая функция, не обязательно читающая, поэтому выводы осторожные:

- **Указатель текста `0x02075A28`**: пишет только обработчик `TEXT_EX` (`0x02049234`, 15 записей за прогон, значения `0x02303350`, `0x02303454`, `0x02303564`… — по реплике), нигде не обнуляется. Читает его код вокруг `0x02047780…0x02047DE4` (по `fn` — вызовы `0x0201929C`/`0x020192EC`, интерполяция); эта функция в 780 строк C ещё читает флаги `0x0207596C+0x48/+0x4C` и `0x020758EC+0x74`, которые ставит `TEXT_EX`, и метку скрипта `0x0206577C`. То есть это реакция на «пришла реплика» (открытие окна/ведение), точная роль не выяснена.
- **Флаг окна `0x02078598`** (`SHOWWINDOW`/`HIDEWINDOW`): читают функции около `0x0204B577`/`0x0204B583` — это `0x0204AFEC…0x0204BC28` (около 1500 строк C: менеджер объектов `0x0207858C`, читает и `0x02075A20`, вызывает `0x02020E58` 23 раза).
- **Писатель текста `0x02075AFC`** (шрифт `0x0229A828`): читают цепочка вывода букв — `0x02021FDC` (вызов из `0x02021484`), глифовые функции `0x02033280`, `0x020332C8`, `0x020338E0` (вызовы из `0x02021FF6`, `0x02034134`, `0x02034154`, `0x02034220`). Это и есть отрисовка текста; дальше разбирать от `0x02021FDC`.

## 2б. Куда окно диалога пишет (VRAM, `watchw 06000000 80000`, C01_01, кадры 6109–6469)

- Окно — **текстовая плитка в BG**: карта тайлов на `0x06001C8E…0x06001DFC` (строка карты 0x40 байт = 32 слова), записи `0xD001…0xD090`: палитра 13, номера тайлов подряд `1…0x90` = 144 тайла, 6 рядов по 24 тайла = три строки текста по два тайла высотой (24 колонки × 8 = 192 px, текст до 194 px — `dialogue::MAX_WIDTH`). Карту выставляет `0x02034398` (вызов из `0x0203431C`) при каждой новой реплике (кадры 6109, 6169/6229, 6409…); последний ряд 0xD065…0xD090 — со 2-й реплики.
- Данные тайлов (`0x06001800…0x06001854`) очищает `memset`-заглушка `0x01FF8068` из `0x020223DF` (и `0x02009448`) в кадр открытия окна; буквы потом рисуются глифовыми функциями цепочки `0x02033280/0x020332C8/0x020338E0` через писатель `0x02075AFC` (шрифт `0x0229A828`).
- Следствие для нативного пилота: границу «состояние vs отрисовка» (шаг 164.2) проводит этот интерфейс: тайловая карта и данные тайлов лежат в VRAM DS (привязка к железу, п. «привязки к DS» ниже).

### Привязки к железу DS (по мере разбора)

1. BG-карта и данные тайлов окна в VRAM DS (`0x06001Cxx`, палитра 13), запись прямо в VRAM.
2. Окно открывается при `TEXT_EX` (метка скрипта `0x14`) и держится по флагу `0x02078598`; таймингом vblank пока не измерено.
3. Ввод: клавиши опрашивает `0x0201F8AC` (вызов из `0x0202375A`): `REG_KEYINPUT` (`0x04000130`) | `0x027FFFA8` (клавиши ARM7) → структура `0x0206B340`: `+4` нажато в этом опросе, `+6` отпущено, `+8` удержано (`0x2FFF` — маска кнопок и касания). Это привязка к железу DS (регистр клавиш), на нативном слое заменяется логическими событиями `Button` (`docs/NATIVE-ENGINE-DESIGN.md` п. 4).
4. Кто читает `+4/+8` (структура `0x0206B340`): в кадрах ожидания нажатия (8115–8120, реплика «Better head to the lobby.») читают структуру код `0x0202CA50` (вызов из оверлея, `lr = 0x020A0699`) и `0x02029A54` (из `0x0202385E`). Читатель найден: оверлей **ov4**, функция `0x020A0620` (`p_arm9_ov4_000.c`), покадровая: если событийный режим и `0x0202CA50` (геттер `[obj+0x2C]`) равен 0, то при бите `0x800` в «нажато» `0x0206B344` (по маске `0x2FFF` это Y) вызывает `0x020246AC(6)` (действие 6, роль не выяснена); дальше проверки `0x020510EC` и флагов `[ov4+0x23AA4/0x23AA8]`, вызовы `0x0202C96C`/`0x0202C84C`/`0x02025CB8(0x43)`, запись `0x0207862C+0x5C`. То есть ov4 — обработчик ввода событийной сцены (меню по Y и подобное), а не переход реплики по A; A для следующей реплики берётся не отсюда, а из `0x0206CA72` (п. 2в). Атрибуция по `fn` ненадёжна (последняя вошедшая функция), `0x0202CA50` — только геттер; настоящий читатель — в оверлее `0x020A06xx`. В ранних репликах C01_01 (кадры 6109–6469) смена реплики идёт по таймеру скрипта (`WAIT`), ввод не читается.

## 2в. Переход реплики по A (K-182, найдено 2026-11-08)

Ожидание нажатия живёт **внутри шага сценария** `0x02045BC4` (блок `0x0204669C…0x0204677A`, `p_arm9_012.c`), а не в обработчиках и не в оверлее.

Цепочка (C01_01, кадры 7427–7490, A на два кадра из двадцати):
1. `<TEXT_EX>` (`0x02049234`) ставит метку `0x0206577C = 0x14`; шаг каждый кадр уменьшает метку, пока она больше 0 (`0x0204669C…0x020466A6`): это фаза печати/окна, 20 кадров.
2. `<WAIT>` (`0x02048078`) ставит метку `-1` (`0xFFFFFFFF`) и флаг ожидания `0x020758EC+0x78 = 1`; если `[0x020759EC+0xC] == 0`, вызывает `0x020532B0(obj [0x0207596C+0x40], 1)` — включает у объекта полуслово `+0x1A` (значок «ждём нажатия»).
3. Шаг при метке `-1` и режиме окна `[0x0207596C+0x3C]` (геттер `0x0202CA50`) не равном 4: `+0x78` 1→2 (первый проход); при 2: если `[0x0207862C+0x5C] != 0` — вызов оверлея `0x020A0788(3)`; затем `+0x78 = 0` (`0x020466E2`).
4. **Проверка A:** `*(u16*)0x0206CA72 & 1` (кнопка A «нажата» в этом кадре) **или** `[0x0207862C+0x68] != 0` (признак принудительного перехода: автопрокрутка/пропуск, роль не проверена). Если ни то ни другое — переход на `0x020468AC`, ждём дальше.
5. Иначе (`0x020466FC`): `[0x0207596C+0x4C] = 0`, `0x020532B0(obj, 0)` (значок гаснет), если `[0x0207862C+0x5C] != 0` — оверлей `0x020A0788(4)`; метка `0x0206577C = 0`, `+0x78 = 0`; при `[0x020759EC+0x18] == 0` — закрытие окна: `0x0202143C` (режим 3), `0x020533F0(obj, 0x70, 0x99)`, `0x020213F8`, `[0x020758EC+0x70] = 0`, `[0x020759EC+8] = [0x020759EC+4] = 0`. Дальше шаг берёт следующую команду.
6. Источник A: `0x0202C374` (вызов из `0x02000C62`, на каждом кадре) читает `REG_KEYINPUT` и пишет «нажато в этом кадре» в `0x0206CA72`; это второй набор клавиш, отдельный от `0x0206B340` (п. 2, опрашивает `0x0201F8AC`).

Проверено трассой (`watchw 0206CA70 4 100000 r`, 100 раз `press A 2` + `run 18` до кадра 7427, потом 8 раз): запись `0x0206CA72 = 1` на кадре 7427 из `0x0202C374`, чтение в шаге (кадры 7469, 7473, 7475…) и в `0x020A0788`-ветке. Признак принудительного перехода `+0x68` — не проверялся.

Следствие для пилота (вариант А): подмена `WAIT` меняет лишь поля из п. 2; условие «A нажата» читает шаг, не обработчик, поэтому нативная модель может предсказывать переход, читая `0x0206CA72`, но подменять его в пилоте не нужно. Привязка к железу DS: `REG_KEYINPUT` в `0x0202C374`.
