# Проект интерфейса нативного движка (K-166, эпик 2б/6)

Черновик от 2026-11-06 для утверждения автором (КТ ручная). До утверждения код не пишем. Основание: `docs/NATIVE-SCRIPT.md` (формат скриптов, карта 132 команд), `docs/SINGLE-SCREEN.md`, `crates/sunpetal-app/src/layout.rs`.

## 1. Проблема

Сейчас решения «что на каком экране» принимаются по пикселям: `layout::lower_wanted`, `led_under_panel`, `counter_in`, `hint_in`, `portrait_left`, `edo_in`, `collection_in`… Это эвристики по готовой картинке: ломаются при смене текстур (PS2-пакет, моды), не работают без запущенного ARM-кода и не переносятся на движок, где картинки как таковой на этом уровне нет. Нативному движку нужен обратный порядок: **сцена сама заявляет своё устройство, платформа раскладывает**.

## 2. Границы ответственности

| Движок (логика, не знает про окно) | Платформа (знает про окно, не знает про сюжет) |
|---|---|
| Состояние игры, скрипты, переменные, сохранения | Раскладка: один/два экрана, масштаб, пропорции, врезки |
| Описание сцены (п. 3) | Выбор раскладки по описанию + настройкам игрока |
| Логические выходы: экран 0 и экран 1 (текстуры) | Окно, safe-зоны, поворот, 3DS: всегда два |
| Логические входы (п. 4) | Перевод физического ввода (мышь, пальцы, геймпад) в логические события |
| Звук как события (play/stop/pause) | Аудиоустройство, микшер |

Правило: движок никогда не спрашивает «сколько экранов у платформы». Два логических экрана есть всегда; платформа решает, показывать оба или один.

## 2б. Принцип: никакого хардкода (решение автора 2026-11-06)

Движок не содержит значений, специфичных для игры. Всё, что можно назвать числом, именем или списком из игры, лежит в данных, которые читает движок и которые может заменить мод:
- пороги и скорости (шаг/бег, порог по радиусу круга, мёртвая зона, скорость поворота, `run_allowed`, `walk_speed_max`);
- раскладки, прямоугольники `touch_areas`, умолчания представлений по ролям (п. 5), заплатки;
- таблицы: команды сценария (код → имя → обработчик), сцены, карты, двери, предметы, звуки;
- ориентация камеры, центры и радиусы элементов интерфейса (круг карты (128, 97) r ≈ 82 и подобные числа из замеров);
- версии и совместимость (`engine_api`).

Правила:
1. В коде движка допустимы только механизмы (как читать, как применять), значения приходят из данных. Число в коде без ссылки на данные — дефект при ревью.
2. Каждое значение из замера оригинала записывается в данные вместе с источником (файл, адрес, документ замера), чтобы его можно было проверить и заменить.
3. У данных есть схема и проверка при загрузке (границы, обязательные поля, версия), ошибка понятная.
4. Данные игры (DS) и данные модов одного формата; встроенные значения — файл по умолчанию, не константы.
5. Проверка: тест «в крейте движка нет игровых констант» (поиск чисел из списка замеров) и тест, что замена файла данных меняет поведение.

Следствие для замеров (K-169 и далее): каждый замер заканчивается строкой данных (значение, источник), а не константой в коде.

## 3. Описание сцены (`SceneView`)

Данные, публикуемые движком каждый кадр (или при смене):

- `main`: `Top | Bottom`: какой логический экран несёт картинку сцены.
- `bottom_role`: `None | Map | Menu | Puzzle | Device | Suitcase | Book | Request | Touch(areas)`, чем является нижний экран.
- `touch_areas`: список прямоугольников нижнего экрана, принимающих касание (в координатах DS 256×192).
- `swap_ok`: можно ли одноэкранному режиму переключаться на нижний (головоломка без нижнего экрана непроходима → `false`: обязателен показ нижнего).
- `needs_bottom`: нижний экран обязателен для прохождения прямо сейчас (головоломки, устройство Катарины, чемодан). Тогда одноэкранная раскладка берёт врезку (`puzzle_panel`) или переключение, по настройке игрока.
- `hud`: что на нижнем экране «лёгкое» и может уйти в заплатку (счётчик, подсказка, Эдо: нынешние `Patch`).

Источники значений в порядке надёжности: (1) сценарий (`<SETSCREEN>`, `<ACTSCREEN>`, `<CALLKATHARINE>`, `<SHOWWINDOW>`/`<HIDEWINDOW>` уже несут часть смысла); (2) сцена кода (меню, чемодан, устройство: таблица «сцена → описание», заполняется по `docs/RECON-SCREENS.md`); (3) пиксельные эвристики остаются **только как запасной путь** на ARM-гибриде и выключаются, когда описание есть.

Версия: поле `view_version` (п. 7).

## 3б. Представления сцены, моды и два уровня интерфейса

Одноэкранный показ сцены с `needs_bottom` — **представление** (`Presentation`), выбирается настройкой игрока: `swap` (переключение), `inset` (врезка) или `mod:<имя>`. Мод, например в стиле PS2, получает `SceneView` и обе логические текстуры и сам собирает один кадр; если у мода нет представления для сцены, берётся встроенное (частичный мод ничего не ломает). Привязка: к сцене или ко всем сценам с `needs_bottom`.

Контракт ввода зависит от сцены, `bottom_role.ui`:

1. **`Geometric(areas)`**: набор действий тот же, что в DS; мод переставляет и перерисовывает элементы, каждой кнопке соответствует точка нижнего экрана DS, мод синтезирует касание. Единственный уровень, пока интерфейс исполняет ARM (врезка, головоломки).
2. **`Model(kind, schema)`**: движок отдаёт модель интерфейса (для чемодана: предметы, состояния, выбор, доступные действия, описания), мод рисует как хочет и присылает логические действия (`Action{suitcase.select, id}`). Нужен там, где раскладка и возможности отличаются (чемодан PS2). Возможен только для подсистем, уже перенесённых в нативный движок (чемодан, Guide Book, Request: после K-163…K-165); действия, которых нет в DS, движок реализует сам.

Если у сцены нет модели, мод ограничен геометрическим уровнем или встроенным представлением. Таблица «сцена → есть Geometric / есть Model» ведётся рядом с таблицей сцен; пока для чемодана, Book и Request «модели нет». Форму моделей определяет разведка K-168 (сравнение чемодана DS и PS2). Риск: кадры мода не проверяются GPU-паритетом, эталон — только для движка; ассеты PS2 — из `sunpetal.data`, не из репозитория.

### Чемодан, Guide Book, Request: DS и PS2 (K-168, разведка по готовым снимкам и документам)

Источники: `RECON-SCREENS.md` (дополнения PCSX2 27.10), `SINGLE-SCREEN.md` A.1.1, `DEVICE-PS2.md`, `TRANSLATION-RECON.md`. Новых прогонов не делалось; что не снято, помечено «?».

| Подсистема | DS (факт) | PS2 (факт по снимкам) | Расхождение |
|---|---|---|---|
| Вход в чемодан | значок на нижнем экране ходьбы (START → полоса значков), затем касание перехода | кнопка (SELECT = Y игры), экранной кнопки нет | другой способ входа; для модели это `Action{suitcase.open}` |
| Пункты чемодана | GUIDE BOOK, MEMO, SAVE, GOODS; в головоломке MEMO, PORT, GOODS | органы схемы: Dial, Juck, Guide Book; MEMO, SAVE, GOODS на схеме нет (?) | набор пунктов зависит от версии и от режима (ходьба / головоломка) |
| Guide Book | растровые страницы (48 файлов), Page Select стрелками касанием | страница слева, панель номеров, миниатюра разворота, Page Select; текстовые страницы живым текстом, стрелки прокрутки | у PS2 есть прокрутка текста, у DS её нет; данные страниц разные |
| MEMO | поле на оба экрана, рисование по обоим | не найдено (?) | только DS; единственный пункт, где касание по верхнему экрану |
| SAVE | Yes/No внизу, подсказка наверху, в любой момент | сохранение только у стойки Эда между главами | только DS; в PS2 действия нет |
| GOODS | список профилей 01–11, прокрутка, портрет и описание наверху | ? | не снято в PS2 |
| Request | три кнопки R-00/R-01/R-02, Next, Back; подсказка Эдо наверху | пункт главного меню Request; список ? | не снято подробно |
| Выбор в диалоге | касание | ○ подтвердить, × отменить | кнопочная замена касания |

**Вывод для формы модели.** Общего «чемодана» нет: PS2 — не надмножество DS. Модель описывает не раскладку, а данные и действия:

```
Suitcase { mode: walk | puzzle,            # откуда открыт
           items: [Item{ id, kind, enabled }],   # guide_book, memo, save, goods, port ...
           open: Option<item id> }
GuideBook { page_count, spread, text_pages: [...] , scroll }   # данные страниц из ресурсов, не из кода
Goods     { profiles: [...], selected, scroll }
Memo      { canvas, strokes }               # рисует мод или движок
Action:   suitcase.open | suitcase.close | suitcase.select(id) | guide.page(n) | guide.scroll(dy)
          | goods.select(n) | memo.stroke(points) | save.confirm(bool) | request.pick(n)
```

Правила: (1) `items` и их `enabled` — данные сцены, не зашитый список (принцип 2б); мод показывает только то, что есть, и не обязан рисовать пункты, которых в его версии нет (SAVE, MEMO). (2) Действие, которого нет в DS (прокрутка текста Guide Book, текстовые страницы), движок реализует сам над данными; мод может не использовать. (3) `memo.stroke` требует ввода по обоим логическим экранам: единственное исключение из «касание только нижнего». (4) Вход (`suitcase.open`) в PS2-стиле приходит с `Button`, в DS-стиле с `Touch`; модель не знает, как он вызван.

Не решено: нужны снимки PS2 для GOODS и Request, подтверждение, что в PS2 нет MEMO (по схеме органов её нет, но схема может показывать не все пункты). Перед кодом модели (K-164/K-165) эти два пункта снять у автора.

## 4. Ввод

Логические события (движок):
- `Touch{down|move|up, x, y}` нижнего экрана (координаты DS, стилус и палец не различаются);
- `Button{A,B,X,Y,L,R,Start,Select,Dpad*}`;
- `Move{x, y}`: вектор ходьбы −1…1 (мёртвая зона на стороне платформы). Источники: левый стик (непрерывный, как PS2), D-pad и клавиатура (8 значений), стилус/палец в мире (точка касания относительно героя → направление и величина; на DS так даётся гибкое направление, по слову автора 2026-11-06, в коде не проверено). Вектор в экранных осях, в мировые переводит движок через камеру. Пока ходьбу исполняет ARM, платформа квантует `Move` до 8 направлений (совместимость гибрида); режим «как в DS» (квантование) остаётся для прогонов и сравнения. Замер K-169 (`docs/NATIVE-INPUT.md`): в оригинале направление непрерывное (стилус: угол от центра круга карты) или в 8 значениях (D-pad), мёртвой зоны у стилуса нет; скорость — две ступени: шаг (касание ≤ 40 px от центра круга, половина радиуса) и бег (> 40 px; D-pad по умолчанию бег, B замедляет до шага), где сцена разрешает бег (на парковке C19_01 есть, в помещениях нет; замер парковки 2026-11-06). Контракт: `Move{x, y}` несёт угол и величину; по умолчанию величина ≤ 0,5 — шаг, > 0,5 — бег (порог данные, не код), модификатор «шаг»; признак `run_allowed` — параметр сцены/карты (найден в K-173, `NATIVE-INPUT.md`: данные ARM9 по диапазонам номеров карт, бег запрещён на 30–32, 37–59, 88; скорости 274 / 819 / 1638 в 1/4096 за шаг обновления — всё это строки данных, не код). Плавная скорость по наклону стика — опция по флагу. Правило платформы: стик (в т.ч. круговой пад 3DS) всегда идёт в `Move` как вектор и никогда не сводится к D-pad; на DS ходьба возможна и по D-pad (8 направлений), и по стилусу, а на 3DS стик, приравненный к D-pad, теряет аналог (слово автора 2026-11-06, в коде не проверено). Опция «запомнить камеру» (`move.latch_camera`, по умолчанию выключена, идея автора 2026-11-06): пока стик наклонён, перевод «экран → мир» остаётся таким, каким был в начале движения, и при повороте или переключении камеры герой идёт туда же, куда шёл; когда стик вернулся в мёртвую зону, перевод сбрасывается и следующий наклон считается от текущей камеры. Вариант А (предлагается): перевод держится до отпускания; вариант Б: пересчёт при резкой смене направления (> порога). Смена карты (`<CHANGEMAP>`) всегда сбрасывает. Для стилуса — отдельный флаг `move.latch_camera_stylus` (по умолчанию выключен, по слову автора 2026-11-06: в оригинале так не работает и нравится не всем): перевод фиксируется в момент касания и держится, пока палец или стилус на экране; сброс при отрыве, если касание двигается, вектор считается по точке касания, но с зафиксированным переводом. Недоступна, пока ходьбу исполняет ARM, и в режиме «как в DS»; качество жизни, в паритет с DS не входит. Риск: плавный вектор даёт движение вдоль стен и углов, которого в DS не было, нужна проверка коллизий на узких местах.
- `Action{id, args}`: семантическое действие интерфейса (п. 3б, уровень `Model`);
- служебные не идут в движок: смена раскладки, пауза платформы, скриншот.

Платформа переводит: мышь/палец на одноэкранной раскладке → `Touch` через обратное преобразование раскладки (`touch_safe` уже есть); врезка → касание в панель; геймпад → `Button`; экранные кнопки (`touchpad.rs`) → `Button` или служебное. Касание на экране, который сейчас не показывает нижний, игнорируется, кроме `swap_ok`-переключения жестом.

Это даёт то, что нужно для Ayn Thor и телефона: оба режима равноправны, тач работает в каждом; на 3DS — те же события от настоящего стилуса.

## 5. Раскладки

Остаются данными (`layout.rs`, В.3): `stacked`, `side_by_side`, `single(top|bottom)`, `overlay`, `puzzle_panel`. Меняется только вход выбора: вместо `lower_wanted(rgba)` — функция `choose(view: SceneView, prefs: Prefs) -> Layout`, чистая и тестируемая без кадров. Таблица решений:

| `bottom_role` | Нужен верхний экран, пока открыт нижний | Представление по умолчанию («один экран») |
|---|---|---|
| ходьба, диалог, карта/HUD (`needs_bottom` нет) | да | `single(main)` + заплатки (счётчик, подсказка, Эдо) |
| чемодан, Guide Book, Request, меню | нет (верхняя панель не нужна) | `swap`: `single(bottom)` |
| головоломка, устройство Катарины | да (сцена и подсказки Эдо наверху) | `inset`: `overlay(panel)` |

В режиме «два» всегда `stacked`/`side_by_side`. Умолчание задаётся ролью в данных, игрок может переопределить его по каждой роли; мод (в т.ч. стиль PS2) заменяет представление для нужных ролей (п. 3б). Если `swap_ok` ложно (нижний экран обязателен), `swap` недоступен, остаётся `inset`.

Переключение экранов на одном экране: кнопка (всегда) и жест (долгое касание края; опция в настройках, по умолчанию выключена, решение автора 2026-11-06). Жест не должен перехватывать касание, нужное сцене.

3DS: `prefs` фиксирует два экрана, строки с одним экраном не используются.

## 6. Состояние и сохранения

Сейчас сохранение — слепок ARM-памяти/SRAM формата DS. Нативный движок вводит собственное состояние (`GameState`: переменные скрипта, позиция в скрипте, флаги коллекции, звук) с собственным форматом и **импортёром** из DS-сохранения (`.sav`), чтобы прогресс игроков не терялся. Экспорт обратно в DS — не цель.

Инструменты разработки зависят от сохранений: `--goto Cnn_yy` проходит в сцену через меню запросов на сохранении, где всё открыто (`build/full100.sav`), от него же зависят `screen-walk`, QA-скрипты, дампы кадров для паритета GPU (решение автора 2026-11-06: иметь в виду). Поэтому:
- **Импорт `.sav` нужен с первого запуска нативного движка** как минимум для отладки (игроку «новая игра» допустима раньше); без него автоматизация перестаёт работать.
- Нативный движок получает собственный `goto` как часть отладочного интерфейса: загрузка сцены по `Cnn_yy` с заданным набором переменных и флагов (из `.sav`-импорта или таблицы), без прохождения меню. Он быстрее и не зависит от ARM.
- Отладочный интерфейс (REPL `sunpetal-debug`, `peek`, `shot`, `calls`) переносится на движок: `peek` читает `GameState`, а не RAM; команды `goto`, `press`, `tap` остаются с теми же именами.
- Отдельная карточка: разведка формата `.sav` (до K-164) и критерий «`--goto` и `screen-walk` работают на нативном движке» как условие закрытия K-165.

## 7. Версия интерфейса для модов

`engine_api = 1`: набор `SceneView`, логических событий и команд сценария (132 + расширения). Мод объявляет минимальную версию; движок отказывает с понятной ошибкой. Добавление полей — минорная версия (по умолчанию значения), смена смысла — мажорная. Мод может задавать свои `SceneView` для своих сцен (данные рядом со сценарием), нижние экраны модов описываются тем же способом.

### Данные сцены в моде (`touch_areas`)

Мод с собственной сценой (например, головоломкой) объявляет рядом со сценарием поля `bottom_role`, `needs_bottom`, `swap_ok`, `touch_areas` (список прямоугольников нижнего экрана в координатах DS 256×192). Платформа по ним выбирает представление (врезка или переключение), направляет касания, рисует подсказки и экранные кнопки; кода платформы мод не получает. Области могут меняться по ходу сцены (команда сценария обновляет список).

Проверка при загрузке мода: прямоугольники внутри 256×192, при `needs_bottom` список не пуст, роль известна; иначе мод отклоняется с понятной ошибкой. `swap_ok = false` вместе с отсутствием врезки делает сцену непроходимой на одном экране: предупреждение в журнале. Режим отладки рисует области поверх кадра. Относится к уровню `Geometric` (п. 3б); для `Model` области не нужны. Поля `touch_areas` входят в `engine_api`: смысл менять только с мажорной версией.

## 8. Гибрид на переходе

Пока часть команд (эффекты, ~39 из 132, см. NATIVE-SCRIPT §8) исполняет ARM, `SceneView` для их сцен берётся из таблицы «сцена → описание» (п. 3, источник 2) или, если записи нет, из старых эвристик. Метрика готовности: доля кадров глав 1–19 (`screen-report`, 463 кадра), где описание получено не из эвристик.
