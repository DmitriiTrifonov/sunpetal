# Нативный скриптовый движок: разведка (эпик K-160…K-166)

Цель автора (2026-11-06): исполнять скрипты игры своей виртуальной машиной вместо ARM-кода игры; моды; отвязка от железа DS (экраны остаются логическими: см. K-166). Здесь результат шага 1/6 (K-160), только чтение: игровые файлы не менялись, текст игры в документ не попал.

Источник файлов: `~/Developer/games/fsar-ru/extracted/data` (распаковка ROM проектом перевода, только чтение). Совпадение с нашим дампом `YHNP` (SHA-1 `4922df25…`) не сверялось, это предположение.

## 1. Главное: скрипты сцен — текст, не байткод

- Файлы `Chapter/Pack/CNN/*.txt.z`: LZ10, внутри UTF-16 с BOM, **теги-команды** вида `<ИМЯ>`, строки аргументов, `</ИМЯ>`. Аргументы разделены переводом строки или табуляцией; `//` — комментарий до конца строки (японский, из ROM). Метки: `[[имя`; переход `<JUMP>` на метку; конец — `<END>`.
- Реплики лежат отдельно, в `*.s.z` (то же сжатие, формат `[[ID` + текст, разбирается `crates/sunpetal-data/src/script.rs`); из скрипта на них ссылаются `<TEXT_EX>` с ID. То есть диалог = данные, логика = теги.
- Ветвление: `<CHANGEBYVALUE>` (номер переменной, число ветвей, пары «верхняя граница → метка»), `<JUMP>`, переменные `<SETVALUE>`, `<ADDVALUE>`.
- Рядом с главой лежит `CNN.EVN`: двоичная таблица событий (записи с именем файла сцены, например `C01_01.TXT`, и числовыми полями). Заголовок и записи разобраны в разделе 4, смысл полей — нет.

Вывод: интерпретатор скриптов в игре — это разбор текста по тегам, а не эмуляция опкодов. Для нативной ВМ это самый удобный случай: формат уже данные, читаемый и правимый моддером без инструментов.

## 4. Проверено и разобрано дальше (2026-11-06)

**Источник совпадает с нашим ROM.** `tools/script/nitrofs_list.py ROM --compare ~/Developer/games/fsar-ru/extracted/data`: в NitroFS нашего дампа (`YHNP`) 6666 файлов, все 6666 совпадают побайтно с распаковкой проекта перевода. Значит опись из раздела 2 относится к нашему ROM.

**Скрипты не зависят от языка.** В каталогах `de/es/fr/it/ue` внутри `Pack/Cxx` лежит 87 файлов `*.txt.z`, и все они называются `dummy.txt.z` (в них нет тегов). Языковые у каждой сцены только реплики `*.s.z` (3198 файлов: по `C01_01` общий и по одному на язык). Это упрощает ВМ и моды: логика одна, текст подставляется по ID.

**Прочие файлы с текстом** (не `*.txt.z`): 691 обычный `*.txt` (в основном `Profile/<язык>`, `EdoComment/<язык>`, `2D/<язык>`: подписи и сообщения, не скрипты) и `*.cam` (72) / `*.CAM` (7). Их формат не смотрели.

**Формат `CNN.EVN`** (20 файлов, по главе; данные не меняли):
- Заголовок 0x88 (136) байт: `u32` номер главы, `u32` число записей N, `u32` 0x44, остальное нули.
- Затем N записей по **104 байта**. Имя файла сценария или объекта — строка с нулём в смещении `+44`, длиной не меньше 20 байт (например `C07_101_SoccerBall.TXT`). Остальные поля: целые, часть со знаком (координаты в 20.12, например `0xffffcd1f` похоже на отрицательное фиксированное число), и в записи есть смещения в хвост файла.
- Последняя запись каждого файла — признак конца (`0x01` на месте имени).
- Всего 1422 записи на 20 глав, у 1361 есть имя; различных имён `*.TXT` 950. У остальных имя не `.TXT`: имена объектов (`track`, `book`, `rock`, `KURUMA`, `TRUCK`, `natsuko`, `takaoka1`…), то есть EVN описывает не только сцены, но и актёров/объекты карты.
- Не разобрано: смысл полей записи (какое поле — карта, позиция, условие запуска, радиус), хвост файла (с 4920 для C01; 1860 байт после записей).

## 6. Следствия для проекта (пока предположения)

- Для **модов** формат уже годится как есть: `*.txt` правится как текст, реплики лежат отдельно. Свой чистый формат поверх (K-166) нужен, только если захочется отвязаться от тегов-DS (координаты, ID моделей, номера звуков).
- Для **отвязки от DS** главные привязки лежат в аргументах (номера моделей/движений/звуков игры, мировые координаты DS) и в том, что `WAITFRAME` считает кадры DS (60 Гц). Это то, что K-166 должен вынести в платформенный слой или таблицы.
- Для **порта на 3DS** это сильный довод в пользу нативного движка: ВМ потока маленькая, всё тяжёлое — это движок под тегами, и его можно писать с нуля, без рекомпилированного ARM.

## 7. Карта движка, первый проход (K-161, 2026-11-06)

**Где в ARM9 лежат имена команд.** ARM9 (`0x02000000`, в файле ROM с `0x4000`, не сжат) хранит имена тегов строками UTF-16 (`<ИМЯ>` и `</ИМЯ>`) и два массива указателей на них:
- **Открывающие теги:** `0x0206556C…0x0206577C`, **132 записи** (по 4 байта), порядок = номер команды: `TEXT, TEXTPOS, TEXTCOL, NEXTPAGE, SUBTEXT…, WAIT, LABEL, JUMP, JUMPFILE, JUMPFILELABEL, SETIMAGE…, WAITFRAME, …, END, SETVALUE, ADDVALUE, CHANGEBYVALUE, …, BGM_PAUSE, SE_PAUSE`. Перед ними на `0x02065568` стоит указатель на строку `<R>` (разделитель строк реплики).
- **Закрывающие теги:** `0x02065454…0x02065564`, массив той же формы (`</CHARFOCUS2>` … `</SE_PAUSE>`).
- Все **84 команды из скриптов (раздел 2) есть в таблице**. Ещё **48 команд заведены в игре, но ни в одном сценарии не встречаются** (`CHOICE`, `LABEL`, `JUMPFILE`, `JUMPFILELABEL`, `SETIMAGE`, `PUTIMAGE`, `REMOVEIMAGE`, `SETNEXTBG`, `TRANSBG`, `SUBTEXT*`, `SETCAMPOS2`, `MOVECAMERA2`, `CHARLOOKAT`, `SETFACE`, `SETFOVY`, `EYEBEAM`, `RADIATE`, `RING`, `SMOKE`, `LIGHTER`, `DEATHBALL`, `EXPLODE2/3`, `PLAYCAMMOTION` и др.). Для нативной ВМ это отложенная часть: игра их умеет, готовые сценарии не используют; для модов они доступны.

**Что пока не найдено.** Прямых ссылок из кода на начало массива нет (в пулах литералов нет `0x0206556C` и `0x02065640`), поэтому не ясно, как игра по имени выбирает обработчик: перебор массива со сравнением строк и затем `switch` по номеру, или таблица функций где-то ещё. Адрес `0x02065568` встречается в пулах литералов около 90 раз у функций в `0x0203F7F4…0x02045690`; они лежат подряд и, возможно, и есть обработчики тегов, но привязка «номер тега → функция» не доказана.

**Следующий шаг (нужна динамика).** Трасса на запуске сцены: по `script_step()` и текущему адресу команды (`0x02075988`) записывать пары «номер тега → адрес вызванной функции игры». Для этого нужен инструмент в `sunpetal-debug` или скрипт REPL по скиллу `screen-recon`; он покажет по каждой команде, какие функции она вызывает (камера, персонажи, звук), и даст карту «опкод → функция ARM → подсистема».

**Как воспроизвести.** Читать строки UTF-16 из ARM9 ROM по смещению `0x4000` (длина `0x6E258`) и искать массив подряд идущих указателей на строки `<…>` (в репозиторий этот скрипт пока не добавлен).
