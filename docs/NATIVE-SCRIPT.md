# Нативный скриптовый движок: разведка (эпик K-160…K-166)

Цель автора (2026-11-06): исполнять скрипты игры своей виртуальной машиной вместо ARM-кода игры; моды; отвязка от железа DS (экраны остаются логическими: см. K-166). Здесь результат шага 1/6 (K-160), только чтение: игровые файлы не менялись, текст игры в документ не попал.

Источник файлов: `~/Developer/games/fsar-ru/extracted/data` (распаковка ROM проектом перевода, только чтение). Совпадение с нашим дампом `YHNP` (SHA-1 `4922df25…`) не сверялось, это предположение.

## 1. Главное: скрипты сцен — текст, не байткод

- Файлы `Chapter/Pack/CNN/*.txt.z`: LZ10, внутри UTF-16 с BOM, **теги-команды** вида `<ИМЯ>`, строки аргументов, `</ИМЯ>`. Аргументы разделены переводом строки или табуляцией; `//` — комментарий до конца строки (японский, из ROM). Метки: `[[имя`; переход `<JUMP>` на метку; конец — `<END>`.
- Реплики лежат отдельно, в `*.s.z` (то же сжатие, формат `[[ID` + текст, разбирается `crates/sunpetal-data/src/script.rs`); из скрипта на них ссылаются `<TEXT_EX>` с ID. То есть диалог = данные, логика = теги.
- Ветвление: `<CHANGEBYVALUE>` (номер переменной, число ветвей, пары «верхняя граница → метка»), `<JUMP>`, переменные `<SETVALUE>`, `<ADDVALUE>`.
- Рядом с главой лежит `CNN.EVN`: двоичная таблица событий (записи с именем файла сцены, например `C01_01.TXT`, и числовыми полями). Заголовок и записи разобраны в разделе 4, смысл полей — нет.

Вывод: интерпретатор скриптов в игре — это разбор текста по тегам, а не эмуляция опкодов. Для нативной ВМ это самый удобный случай: формат уже данные, читаемый и правимый моддером без инструментов.

## 4. Проверено и разобрано дальше (2026-11-06)

**Источник совпадает с нашим ROM.** `tools/script/nitrofs_list.py ROM --compare ~/Developer/games/fsar-ru/extracted/data`: в NitroFS нашего дампа (`YHNP`) 6666 файлов, все 6666 совпадают побайтно с распаковкой проекта перевода. Значит опись из раздела 2 относится к нашему ROM.

**Скрипты не зависят от языка.** В каталогах `de/es/fr/it/ue` внутри `Pack/Cxx` лежит 87 файлов `*.txt.z`, и все они называются `dummy.txt.z` (в них нет тегов). Языковые у каждой сцены только реплики `*.s.z` (3198 файлов: по `C01_01` общий и по одному на язык). Это упрощает ВМ и моды: логика одна, текст подставляется по ID.

**Прочие файлы с текстом** (не `*.txt.z`): 691 обычный `*.txt` (в основном `Profile/<язык>`, `EdoComment/<язык>`, `2D/<язык>`: подписи и сообщения, не скрипты) и `*.cam` (72) / `*.CAM` (7). Их формат не смотрели.

**Формат `CNN.EVN`** (20 файлов, по главе; данные не меняли):
- Заголовок 0x88 (136) байт: `u32` номер главы, `u32` число записей N, `u32` 0x44, остальное нули.
- Затем N записей по **104 байта**. Имя файла сценария или объекта — строка с нулём в смещении `+44`, длиной не меньше 20 байт (например `C07_101_SoccerBall.TXT`). Остальные поля: целые, часть со знаком (координаты в 20.12, например `0xffffcd1f` похоже на отрицательное фиксированное число), и в записи есть смещения в хвост файла.
- Последняя запись каждого файла — признак конца (`0x01` на месте имени).
- Всего 1422 записи на 20 глав, у 1361 есть имя; различных имён `*.TXT` 950. У остальных имя не `.TXT`: имена объектов (`track`, `book`, `rock`, `KURUMA`, `TRUCK`, `natsuko`, `takaoka1`…), то есть EVN описывает не только сцены, но и актёров/объекты карты.
- Не разобрано: смысл полей записи (какое поле — карта, позиция, условие запуска, радиус), хвост файла (с 4920 для C01; 1860 байт после записей).

## 6. Следствия для проекта (пока предположения)

- Для **модов** формат уже годится как есть: `*.txt` правится как текст, реплики лежат отдельно. Свой чистый формат поверх (K-166) нужен, только если захочется отвязаться от тегов-DS (координаты, ID моделей, номера звуков).
- Для **отвязки от DS** главные привязки лежат в аргументах (номера моделей/движений/звуков игры, мировые координаты DS) и в том, что `WAITFRAME` считает кадры DS (60 Гц). Это то, что K-166 должен вынести в платформенный слой или таблицы.
- Для **порта на 3DS** это сильный довод в пользу нативного движка: ВМ потока маленькая, всё тяжёлое — это движок под тегами, и его можно писать с нуля, без рекомпилированного ARM.

## 7. Карта движка, первый проход (K-161, 2026-11-06)

**Где в ARM9 лежат имена команд.** ARM9 (`0x02000000`, в файле ROM с `0x4000`, не сжат) хранит имена тегов строками UTF-16 (`<ИМЯ>` и `</ИМЯ>`) и два массива указателей на них:
- **Открывающие теги:** `0x0206556C…0x0206577C`, **132 записи** (по 4 байта), порядок = номер команды: `TEXT, TEXTPOS, TEXTCOL, NEXTPAGE, SUBTEXT…, WAIT, LABEL, JUMP, JUMPFILE, JUMPFILELABEL, SETIMAGE…, WAITFRAME, …, END, SETVALUE, ADDVALUE, CHANGEBYVALUE, …, BGM_PAUSE, SE_PAUSE`. Перед ними на `0x02065568` стоит указатель на строку `<R>` (разделитель строк реплики).
- **Закрывающие теги:** `0x02065454…0x02065564`, массив той же формы (`</CHARFOCUS2>` … `</SE_PAUSE>`).
- Все **84 команды из скриптов (раздел 2) есть в таблице**. Ещё **48 команд заведены в игре, но ни в одном сценарии не встречаются** (`CHOICE`, `LABEL`, `JUMPFILE`, `JUMPFILELABEL`, `SETIMAGE`, `PUTIMAGE`, `REMOVEIMAGE`, `SETNEXTBG`, `TRANSBG`, `SUBTEXT*`, `SETCAMPOS2`, `MOVECAMERA2`, `CHARLOOKAT`, `SETFACE`, `SETFOVY`, `EYEBEAM`, `RADIATE`, `RING`, `SMOKE`, `LIGHTER`, `DEATHBALL`, `EXPLODE2/3`, `PLAYCAMMOTION` и др.). Для нативной ВМ это отложенная часть: игра их умеет, готовые сценарии не используют; для модов они доступны.

**Что пока не найдено.** Прямых ссылок из кода на начало массива нет (в пулах литералов нет `0x0206556C` и `0x02065640`), поэтому не ясно, как игра по имени выбирает обработчик: перебор массива со сравнением строк и затем `switch` по номеру, или таблица функций где-то ещё. Адрес `0x02065568` встречается в пулах литералов около 90 раз у функций в `0x0203F7F4…0x02045690`; они лежат подряд и, возможно, и есть обработчики тегов, но привязка «номер тега → функция» не доказана.

**Следующий шаг (нужна динамика).** Трасса на запуске сцены: по `script_step()` и текущему адресу команды (`0x02075988`) записывать пары «номер тега → адрес вызванной функции игры». Для этого нужен инструмент в `sunpetal-debug` или скрипт REPL по скиллу `screen-recon`; он покажет по каждой команде, какие функции она вызывает (камера, персонажи, звук), и даст карту «опкод → функция ARM → подсистема».

**Как воспроизвести.** Читать строки UTF-16 из ARM9 ROM по смещению `0x4000` (длина `0x6E258`) и искать массив подряд идущих указателей на строки `<…>` (в репозиторий этот скрипт пока не добавлен).

## 9. Нативный интерпретатор в режиме наблюдателя (K-162)

Код: `crates/sunpetal-runtime/src/scriptvm.rs` (фича `debug-tools`), сверка — `Session::check_script`, команды REPL `scriptseq` и `scriptcheck` (`docs/debug-tools.md`). Игра не меняется: порядок команд ведёт ARM-код, нативный разбор текста идёт рядом и говорит, где порядок игры расходится с текстом сценария.

**Как это устроено.**
- Что видим у игры: входы в обработчики шага сценария (`0x02045BC4`), по таблице `docs/native-script-dispatch.csv` (код → адрес обработчика). Это точный порядок выполненных команд, без трассировки каждого кадра.
- Что считаем сами: разбор текста (`Chapter/Pack/Cnn/<сцена>.txt.z`) в список команд и меток, дальше поток: следующая команда по порядку, `<JUMP>` по метке, `<CHANGEBYVALUE>` по значению переменной игры (первая ветка с границей ≥ значения; **выше всех границ — ветки нет, идём дальше по тексту**, проверено на C11_05), `<SETVALUE>`/`<ADDVALUE>` внутри кадра поверх переменных игры, `<END>`. Тег, которого нет в таблице игры (`ON_AIR` и подобные), пропускается так же, как в игре.
- Чтение переменных игры — массив `0x020742EC` (256 слов), снятый в начале кадра.

**Что выяснилось.**
- Сценарий после `<END>` не всегда читается заново: событийные сцены запускаются повторно без чтения файла (C11_05), наблюдатель начинает с начала, если игра идёт с первой команды.
- Сцену игра может запустить с метки, до того как наблюдатель стал смотреть (`goto` возвращается позже начала сценария). Наблюдатель держит все места, где игра могла быть (по первой пачке команд), и отбрасывает несогласные по ходу.
- Таблица `0x02074BEC` / счётчик `0x020740A0` — не список команд сценария (в живой игре она пуста при счётчике 108), в карте движка её не использовать. Текущая команда лежит в куче: `0x02075988` указывает на неё, слово 0 = код, слово 1 = ключ позиции.
- Следующую команду выбирает функция `0x020475E0` по ключу позиции (курсор — `0x0207596C + 0x64`).

**Результат сверки (2026-11-07, `full100.sav`).** Сцены `Cnn_01` глав 1–18 (по 30 000 кадров, автонажатие A): расхождений нет, число совпавших команд равно числу команд в тексте (97–784, всего порядка 3 000). C12_01 переходит на C12_03, C16_01 на C16_LIST (подхват сцены работает). C19_01 — демо титула, команд не шагает; C20 в сохранении закрыта. Сцены с `<CHANGEBYVALUE>`: из 48 таких сценариев удалось открыть 7 (остальные недоступны маршрутом дверей `goto`); на них, включая C10_27 и C14_53 (игра пошла через ветку к концу) и C11_05 (все три ветки и «выше всех»), расхождений нет.

**В приложении (флаг).** `SUNPETAL_SCRIPT_OBSERVER=1` включает тот же наблюдатель в окне: `nds::script_observer_start` вешает наблюдатели на входы в обработчики шага (`debug::watch`, трассировка входов в приложении и так включена `track_script`), после каждого кадра `script_observer_frame` кормит `scriptvm::Observer`; расхождение пишется в stderr строкой `script observer: vblank N: СЦЕНА: что не так` (первые двадцать), раз в 1800 кадров — сводка (`script_observer_summary`: сцена@позиция, сколько команд совпало, расхождений). `nds::script_observer_summary` и `Observer::position` дают сцену и место в её скрипте (для K-115, K-163). Приложение собирается с `debug-tools` всегда (`crates/sunpetal-app/Cargo.toml`), поэтому «обычная сборка» = эта. Без переменной ничего не включается и не стоит ничего. Путь проверен без окна командой REPL `scriptlive FRAMES` (тот же код, что в приложении): C01_01 — 106 команд, C11_05 — 906, C12_01 — 784 (две сцены), расхождений 0, цифры совпадают с `scriptcheck`. В окне не проверено (нужен автор: `docs/qa/K-162.md`).

**Не сделано.**
- 41 сценарий с `<CHANGEBYVALUE>` не проверен на живой игре (нет маршрута `goto`).
- Команды, чьи обработчики не вызываются из шага (`<R>`), и команды с условием в самом обработчике (`TEXT` и подобные с проверкой `[r4+0x20]`) в сверке ловятся только по входу в обработчик.
- Значения аргументов (какой персонаж, какая камера) не сверяются: только порядок и переходы.

## 10. Итог пилота диалога для go/no-go (K-181, 2026-11-08)

План и журнал — `docs/NATIVE-PILOT.md`, разведка — `docs/NATIVE-DIALOG.md`.

**Что сделано и доказано.**
- Нативная модель диалога (`dialogmodel.rs`, числа в `docs/native-dialog-params.csv`) идёт рядом с игрой: слова состояния совпадают каждый кадр, 6 сцен × 3000 кадров, расхождений 0 (`f4c` не моделируется, `mark` берётся у игры при чужих командах: 8–28 раз на сцену).
- Хост-подмена `TEXT_EX`, `SHOWWINDOW`, `HIDEWINDOW`, `NEXTPAGE` за `SUNPETAL_NATIVE_DIALOG=1` (`nativedialog.rs`, данные `docs/native-dialog-hooks.csv`): кадры и слова состояния побайтно равны ARM, 18 сцен × 30 000 кадров и 24 сцены × 6000 кадров, главы 1–18, расхождений 0. Ручная проверка автора (K-164): пройдена.
- Нативный разбор сценария (K-162) и таблицы сцен (K-163) идут за ними; сверка порядка команд на 18 главах без расхождений.

**Чего пилот не доказал (честно).**
- Подмена тонких обработчиков не отнимает у ARM ничего существенного: порядок команд по-прежнему ведёт шаг `0x02045BC4`, рисует и ждёт A тоже ARM. Пилот показал, что тонкие обработчики переносятся в данные дёшево и без риска, но не показал ни нативного ведения порядка, ни нативного рендера или ввода окна диалога (вариант Б не пробовали).
- Не проверены на паритет `CHOICE` (в сценариях не встречается), смена страницы (`NEXTPAGE` пуст, страница ведётся по тексту), тап по тексту, сцены глубоко в главах.

**Что в диалоге привязано к железу DS** (по `docs/NATIVE-DIALOG.md` п. 2б, 2в и «Привязки»):
1. Окно — тайловая BG-карта и 144 тайла в VRAM (`0x06001C8E…`, палитра 13), пишется прямо в VRAM шрифтом-писателем `0x02075AFC`.
2. Ввод: `REG_KEYINPUT` (`0x04000130`) → `0x0206CA72`/структура `0x0206B340`; переход реплики по A — в шаге сценария (метка `-1`, `+0x78`), нативно это событие `Button`.
3. Тайминг: логический шаг сценария идёт раз в 2 vblank, счётчик `mark` считает шаги; анимация значка ожидания (`f4c`) — отдельный счётчик с пиком 42–105, закон не найден.
4. Тап по тексту и касание — через регистры касания DS (не разбирались).

**Объём остальных подсистем** (по `docs/native-script-dispatch.csv` и таблице §8): 132 обработчика, 4917 строк C; тонких (до 20 строк) 71, толстых 61. Как в диалоге, в данные переносятся тонкие; цена растёт с логикой: поток/переменные (11 команд, 556 строк, ядро ВМ: `END` 399 строк), звук (7, 249), карта/сцена (9, 294), экран/видео (6, 160), камера (24, 892), персонажи (19, 1520: поиск персонажа, позы, ходьба), эффекты (39, 960: каждый — спавнер в рендерере/шейдере). Для 48 команд, которых нет ни в одном сценарии, нативная реализация нужна только для модов.

**Время** (`tools/roadmap/timelog.csv`, по часам, паузы не вычитаются): эпик K-160…K-182 примерно 17,6 ч, из них разведка диалога K-174 11,9 ч (включает ночной перерыв, чистой работы заметно меньше), нативная ВМ K-162 2,2 ч, модель и подмена K-177/K-178 0,3 ч, слепые прогоны K-179 0,4 ч. Вывод: тонкие обработчики и паритет-инструменты дёшевы (минуты на подмену), дорога разведка (кто что читает) и толстые подсистемы.

**Для решения K-165 (вердикт за автором; мнение ассистента).**
- Идти (go) в узкой форме: нативная ВМ ведёт порядок команд вместо шага `0x02045BC4` (разбор уже совпадает с игрой), тонкие обработчики — таблицей данных, всё толстое (персонажи, камеры, эффекты, рендер окон и ввод) остаётся на ARM за тем же интерфейсом (гибрид, `docs/NATIVE-ENGINE-DESIGN.md` п. 8). Это даёт скрипты как данные для модов без переписывания рендера.
- Не обещать полной замены движка: следующий дорогой шаг — вариант Б (рендер и ввод диалога) и персонажи; их цену пилот не измерил, нужен отдельный пилот, а не вывод из этого.
- Если цель — мобильные и двухэкранные порты, привязки к железу (VRAM окна, REG_KEYINPUT, vblank) уходят вместе с вариантом Б, то есть без него от DS-слоя избавления нет.

**Решение автора (K-165, 2026-11-08): полное go.** Порты на 3DS и Ayn Thor пока не нужны. План, этапы и порядок — `docs/NATIVE-ENGINE-PLAN.md`; первый этап — измерение (инвентаризация ARM, пилот варианта Б, пилот персонажей), потому что объём толстых подсистем пилот не измерил.
