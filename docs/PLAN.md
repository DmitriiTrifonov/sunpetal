# 🗺️ План: Sunpetal

> Дата: 2026-10-24, актуализировано 2026-10-28, статус: игра играется в окне и на Android; открытые линии — один экран + широкий кадр (8б/8в), чёткий текст (8д), меню в стиле игры (8г), компоновщик 9б (остаток), платформы (10), моды (12). Проект: `Sunpetal (рекомп)` · Инструменты: [Инструменты](TOOLS.md)

Порядок: сначала доказать, что рекомп вообще запускается (одна сцена на десктопе), потом графика и звук, потом пакеты (текстуры, перевод, эффекты), и только потом мобильные платформы и релиз. Сроки не ставлю. Названия проектов-образцов и версии инструментов из памяти, **проверить актуальность**.

## Архитектура (в общих чертах)

1. **Рекомпилятор** (офлайн, запускает пользователь): читает ROM → ARM9/ARM7 код и оверлеи → генерирует C/C++ → собирается в нативный исполняемый файл.
2. **Рантайм**: реализация железа DS (память, DMA, таймеры, прерывания, два 2D-движка, геометрический движок GX, звук ARM7, тачскрин, кнопки) и вызовов библиотек SDK.
3. **Рендерер**: GX-команды → современный GPU (Metal / Vulkan / D3D12 / GL), два экрана, масштаб, шейдерные эффекты.
4. **Система пакетов**: текстуры, перевод (текст, шрифт, графика), шейдерные пресеты подключаются как внешние файлы, оригинал не меняется.
5. **Оболочка**: окно/приложение на каждой платформе, меню настроек, тач-управление.

Образец архитектуры: N64Recomp и Zelda64Recomp (рекомпилятор + рантайм + замена текстур + меню настроек). Для DS готового аналога может не быть, поискать на этапе 0.

## Этап 7б. Файл данных (решение пользователя)

Игрок собирает из своих образов (DS-ROM и PS2-диск) один файл `.spdata` с улучшенными ресурсами; приложение использует его вместо оригинальных там, где замена есть.

- [x] A: формат (`tools/ps2/spdata.py`, секции с тегами), ленивое чтение в рантайме (`Pack` в `texpack.rs`: файл или папка, картинка читается при первом использовании), запись из `mkpack.py`, тесты (фикстура `tests/data/tiny.spdata` читается и Python, и Rust)
- [x] B: сборка файла прямо из DS-ROM и PS2-диска одной командой (`tools/build-data.py`): перечень текстур DS по NSBMD/NSBTX без проигрывания игры (`tools/ds/nitro.py`), ключ палитры теперь по используемому диапазону индексов (иначе статически не посчитать), сопоставление по уменьшенным копиям и точная проверка (цвет, блоки, контуры), запись «любая палитра», непрозрачная текстура DS остаётся непрозрачной. 739 из 1649 текстур (45 %). Остаток: текстуры, которые игра правит в памяти (лица), через `--dump`; сопоставление с несколькими версиями дисков (английский патч)
- [ ] C: модели из PS2 (секция `MODL`): разбор моделей PS2, соответствие DS-моделям, путь отрисовки. Проработка «ультимативной версии» DS+PS2 и порядок слоёв подмены: `docs/ULTIMATE.md` (2026-10-29: основа — DS, качество — PS2 + GPU-бэкенд; GPU-бэкенд и разведка моделей идут первыми)

## Этап 8. Эффекты

- [x] Постобработка в один проход (свой формат параметров, `effects.rs`): чёткие пиксели, строки, сетка LCD, виньетка, цветокоррекция; пресеты none/sharp/lcd/crt/vivid. Не сделано: bloom и прочее многопроходное, slang/librashader
- [x] Bloom и FXAA отдельными проходами после экранов (`post.rs`, работают только когда включены); пресет «мягкое свечение»
- [x] Контур 3D (2026-10-26): `render3d::outline_pass`, по разрыву глубины (вторая разность, плоскость не даёт линии), по смене ID полигона и по границе с 2D; ползунок «Контур 3D», `sunpetal-headless --outline 0-1`. Ширина линии — половина пикселя DS. Линию красит композитор (`compose`, биты 24–27 слова 3D), только там, где 3D видно; полупрозрачные полигоны над пикселем ослабляют её по альфе, интерфейс у ближней плоскости (`INTERFACE_DEPTH`) и пиксели с глубиной от полупрозрачного без линии. Порог `OUTLINE_STEP` подобран на одной сцене (машина), нужны другие
- [x] Мягкие тени (2026-10-26): `render3d::shade_pass`, затенение по буферу глубины (ambient occlusion: пары пикселей по обе стороны на двух расстояниях, плоскость ничего не даёт), биты 28–31 слова 3D, затемняет композитор. Не отбрасываемые тени: у игры нет полигонов-теней (режим 3 в кадрах не встретился), только обычные и тун-полигоны. Ползунки «Мягкие тени» и «Размер теней», `--shadow`, `--shadow-radius`. На сцене с машиной и туннелем меняет ~4% пикселей (мало перепадов глубины), нужны светлые сцены с углами и мебелью
- [x] Сглаживание краёв 3D: супервыборка k×k (`Extras.msaa` 0/2/4, `--msaa`, «Сглаживание краёв 3D» в меню, `[effects] msaa`; 2026-10-28), `render3d::resolve`; аналитическое покрытие по краям (дешевле) не сделано
  - Цена (2026-10-28, замеры агента и пользователя): примерно k² от стоимости 3D; контур и мягкие тени (`shade_pass` растёт как s³) считаются в суперсетке `scale*k`, поэтому 2×2 при «3D 2×» уже тормозит. В окне защита `effects::effective_msaa` (масштаб × выборки ≤ 4), в `sunpetal-headless` без ограничения. Это решение в программном рендере временное: настоящий MSAA осмыслен при **GPU-бэкенде** (аппаратное сглаживание почти бесплатно), пока оставлено как опция по умолчанию выкл, а края смягчает FXAA.
  - Если понадобится быстрее до GPU: (1) контур и тени считать на усреднённых глубине и ID в обычном масштабе, суперсетку держать только для цвета и покрытия; (2) суперсетка только у пикселей на границах полигонов (вариант C, `id`/`cover`/стенсил требуют осторожности)
- [~] **GPU-бэкенд 3D (wgpu) поверх того же потока команд GX**, второй бэкенд, а не замена программного: нужен для скорости при больших масштабах, MSAA, анизотропной фильтрации, мобильных; сложность: воспроизвести точность DS (z/w-буфер, порядок прозрачных, тун-тени, контур по ID, штамп-тест, туман, `extend_sides` для широкого кадра). ## Этап 9б. Компоновщик и `sunpetal.data`

Приложение для игры требует один файл данных, `sunpetal.data`. Его собирает компоновщик (GUI и CLI) на ПК. Если `sunpetal.data` нет, приложение принимает ROM DS напрямую. В репозитории и релизах нет ничего из игры: и компоновщик, и приложение работают у пользователя локально, а `sunpetal.data` и всё, что из ROM, не распространяется.

**Модель (решение пользователя, 2026-10-26)**
- **`sunpetal.data`** — архив с данными игры. Один файл, одинаковый формат на всех платформах, без исполняемого кода. Внутри:
  - данные из ROM DS (обязательная часть);
  - необязательные части: данные из PS2 (улучшенные текстуры, 2D-фоны, экраны), переводы, эффекты, прочие улучшения. Состав набора выбирается при сборке; новые части добавляются позже без смены формата.
- **Компоновщик** собирает `sunpetal.data` из входов: ROM DS обязателен только для сборки `sunpetal.data`; образ PS2, перевод и прочее по желанию. Платформа и набор (профиль) выбираются при сборке: минимальный (DS), с текстурами PS2, с переводом и т.д.
- **Приложение** запускает игру из `sunpetal.data`. Запасной путь: если `sunpetal.data` не собран, пользователь подсовывает ROM DS, и приложение работает прямо с ним (без улучшений, либо с минимальной подготовкой на месте). Так игру можно запустить без компоновщика.
- **На телефонах** (Android, iOS) `sunpetal.data` или ROM пользователь подсовывает файлом через файловый менеджер: диалог выбора и/или папка, которую создаёт приложение (iOS: `UIFileSharingEnabled` и `LSSupportsOpeningDocumentsInPlace`, `Documents` видна в Files; Android: общая папка `Documents/Sunpetal` через SAF, `Android/data` закрыта для файловых менеджеров). По умолчанию на телефоне `sunpetal.data`, собранный на ПК.
