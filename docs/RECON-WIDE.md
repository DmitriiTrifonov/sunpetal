# Широкий кадр: откуда игра берёт матрицу проекции (разведка, 2026-10-27)

Гипотеза: игра сама отсекает объекты за краем кадра 4:3 и не отдаёт их рендереру. Проверка: чтения `CLIPMTX_RESULT` (0x04000640).

- Читает матрицу единственная функция SDK `G3X_GetClipMtx` (`02004EAC`: проверяет бит 27 GXSTAT, при занятости возвращает -1, иначе копирует 16 слов функцией `0200953C`).
- Единственный вызывающий: `02038FAC` (вызов в `02038FE4`). Он ждёт цикл `do { r0 = GetClipMtx(buf) } while (r0 != 0)`: на сцене `C04_03` это 73 067 вызовов за 120 кадров, но почти все — холостое ожидание готовности геометрического движка, настоящее чтение одно за вызов, то есть раз в кадр. Затем `02001F50` переводит матрицу в структуру игры, и ещё `02004EDC` читает векторную матрицу.
- Значит, 1,2 млн «чтений» — это ожидание, а не поточечное отсечение. Матрицу игра сохраняет раз в кадр в свою структуру.
- Опыт: подмена x-строки матрицы при чтении ломает героев (голова на длинной шее, чемодан отдельно): матрица идёт не только в отсечение, а ещё в математику моделей. Откатано.

Дальше: найти потребителей сохранённой структуры (где игра сравнивает проекцию с границами), для этого нужно наблюдение за чтением памяти структуры (адрес в r6 при входе в `02038FAC`), в `sunpetal-debug` есть `traceall` и `cliprep`.
