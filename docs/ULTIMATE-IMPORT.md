# Ультимативная версия: импорт из PS2 через `sunpetal-ee` (исследование и план, 2026-11-11)

Продолжение `docs/ULTIMATE.md`. Там решено, **что** такое ультимативная версия (основа DS, качество PS2, слои подмены). Здесь — **как** довезти модели, анимации, текстуры, звук, видео и «шейдеры» из PS2 в `sunpetal`, опираясь на разбор соседнего проекта `~/Developer/games/sunpetal-ee`.

Задачи для агента `sunpetal-ee` вынесены в `docs/ULTIMATE-EE-TASKS.md` (очередь `X-NN` в формате его `notes/queue.md`). Этот документ — работы на нашей стороне.

Решения из `CLAUDE.md` не пересматриваются: база DS, логика и код только DS, рендерер наш, GPU = софт слово в слово, ассеты в git не кладём, код из GPL не копируем.

## 1. Что нашлось (факты, с источником)

### 1.1. `sunpetal-ee` — что это

Отдельный проект (не git-репозиторий, свой агент, свой цикл `/loop` по `notes/queue.md`): реверс PS2-версии (`SLPS_250.34`) и её статическая рекомпиляция в Rust. За три дня (2026-11-09…11) там получено больше, чем у нас за весь разбор PS2, потому что **ELF не обрезан**: 3131 функция с именами и DWARF 1 со структурами (`notes/types.txt`). Форматы там не угадываются по байтам, а читаются из структур и декомпиляции.

### 1.2. Чем это меняет наши карточки

- **K-153, K-154** (скелет и анимации PS2) — по сути решены там: наш вывод K-153 «привязка вершин к костям из файла не восстановлена» устарел (F-11: кость в DMA-теге).
- **K-199** (узлы без привязки частей у персонажей и мотоцикла) и эвристика `g101_nodes.py` (часть → узел по геометрии, K-184) — заменяются точной привязкой F-11. Эвристику после переезда удалить.
- **K-171 / B-29** (хаотичные треугольники `OP#18`) — причина известна: наш `g101_verts.py` не различает список `0x5b` и полосу `0x5c` и захватывает лишнее за границей GIG (F-10: число вершин совпало только у 50 из 121). Плюс обход граней развёрнут (F-12).
- **K-112** («518 unpaired») — у PS2 есть точная таблица «сцена → запись → модель → текстуры → движения» (F-98, F-99), подбор по окнам не нужен.
- **K-146** (звук из PS2) — получает источник: VAB/SEQ разобраны по составу, музыка в `PCM*.BIN`.
- Наш каталог (597 «моделей» по записям) и их (325 уникальных по SHA-1 тела) считают разное: у них дедупликация между сценами (124 модели встречаются больше чем в одной сцене).

### 1.4. Мосты DS ↔ PS2 (на чём строится сопоставление)

1. **Скрипты.** Обе версии управляются сценариями с одними и теми же действиями: DS `SETMOTION` ↔ PS2 `Chara.MotionPlayback`, `PLAYSE/PLAYBGM` ↔ методы `Se/Seq/Pcm`, `CHANGEMAP` ↔ `Scene3D.SetCurrentScene`, `EXPLODE/SPLASH` ↔ `Task.Call(эффект)`, `PLAYMOVIE/START_TEXMOVIE` ↔ задачи `*_movie`. Главы DS `C00…C19` и сценарии PS2 `OP, R01…R19, R00`. Порядок вызовов внутри сцены даёт таблицу соответствия id без слуха и глаз. **Не проверено:** что порядок сцен и состав действий совпадают настолько, чтобы выравнивать автоматически.
2. **Анимации.** DS: 343 файла `Model/Motion/Mccnn.nsbca`; PS2: 399 уникальных GIM с глобальным `MotionID`. Версия DS — порт, движения почти наверняка пересчитаны из тех же данных. **Не проверено**; проверяется длиной в кадрах и кривыми корня.
3. **Скелеты.** PS2: до 57 костей со «стандартными номерами» (`StandardJointNo`, 62 стандартных). DS: `JNT0` своих моделей. Оба движка жёсткие (одна кость на вершину) — подмена «DS-матрица кости → PS2-часть» возможна без пересчёта весов.
4. **Геометрия мест.** DS `Model/Area/Ann` (карты по id из `CHANGEMAP`) ↔ записи `Scene3D` PS2 (295). Совмещение — преобразованием подобия на карту (масштаб, поворот, сдвиг).
5. **Текстуры.** Уже есть: 816 пар из 1626 ключей DS (K-001).
6. **Ролики.** `movie00.vx` = ролик 0 `MOVIE.BIN` (проверено по планам, `PS2-RECON.md`); `movie01.vx` ↔ ролик 1 (не проверено); мелкие `movie_pda52/binta/daina/utyuu.vx` (6–42 КБ) ↔ `ipum` в NAKA (по именам задач `pda_movie` и т. п., не проверено).

## 2. Решения этого плана

Р-1. **Два потребителя разбора PS2, один источник истины.** `sunpetal-ee` отдаёт *эталонную выгрузку* (`out/export/v1/`, контракт в `ULTIMATE-EE-TASKS.md`). У нас она используется (а) для прототипов и (б) как эталон для **собственного читателя на Rust** в `sunpetal-data`: конечный пользователь собирает `sunpetal.data` из своего ISO одной командой, без Python и без `sunpetal-ee`. Читатель пишется по описаниям форматов (заметки F-NN), не копированием: наши старые эвристические `tools/ps2/g101_*.py`, `g010_*.py` после паритета удаляются.

Р-2. **Анимации: PS2-поза играется у нас, DS даёт «что и когда».** Игра DS продолжает считать свою анимацию и слать матрицы костей. Для подменённого персонажа берём от DS только: какая анимация (`Mccnn`), кадр, матрица корня. Позу костей считаем сами из GIM (57 костей, пальцы) на частоте кадра. Запасной путь (если таблица DS↔PS2 движений не строится): вешать PS2-части на матрицы DS-костей по карте костей. Выбор — ворота У5.6.

Р-3. **Лимит DS расширяем только для подмены** (решение автора 2026-11-11). Лимит 2048/6144 — наша же имитация железа, списки — обычные `Vec`. Подменённые полигоны идут в тот же список, но не считаются в лимит и в счётчики, которые игра читает из регистра (`gx.rs:1410`): для игры кадр выглядит как раньше, её собственные полигоны режутся по правилам DS. Отдельный список с нормалями и float-вершинами понадобится только для попиксельного света (У6.7) и заводится там. Софт рисует всё как эталон, GPU обязан совпасть.

Р-4. **«Шейдеры PS2» = спецификация, а не код.** Микрокод VU1 не исполняем и не транслируем. `sunpetal-ee` выписывает формулы (свет, cel, контур) и даёт тестовые векторы из своего интерпретатора VU1; мы пишем их заново в `render3d.rs` (эталон) и WGSL. Стиль авторский: тун и контур остаются.

Р-5. **Логика, столкновения, камеры, триггеры — DS.** Геометрию столкновений и высот PS2 не импортируем. Риск расхождения визуала с коллизией ловится метрикой (У4.7).

Р-6. **Всё за флагом и по уровням.** `video.graphics = ultimate` (пункт меню уже есть, сейчас недоступен). Каждый слой отключается отдельно: `SUNPETAL_ULT_MODELS`, `_CHARS`, `_ANIM`, `_LIGHT`, `_AUDIO`, `_VIDEO`. Несовпало — рисуем и играем оригинал DS.

Р-7. **Записи между проектами не пересекаются.** Мы читаем `sunpetal-ee/out/export/`, он читает наш репозиторий; никто не пишет в чужое дерево. Задачи ему передаёт автор (файл `ULTIMATE-EE-TASKS.md`).

Открытые вопросы автору — в разделе 6.

## 4. План (этап «У»)

Нумерация `У<трек>.<шаг>`; чекбоксы и журнал — по скиллу `plan-steps`. Зависимость от `sunpetal-ee` помечена `[X-NN]`. Сначала идут шаги с КТ (авто); шаги с автором собраны в конце каждого трека и помечены **(автор)**.

Порядок треков: У0 → У1 → У2 → У3 → У4 (первая видимая победа: сцена PS2 в кадре) → У5 (персонажи) → У6 (свет) → У7 (звук) → У8 (видео) → У9 (эффекты, 2D) → У10 (сборка и выпуск). У7 и У8 от У3–У6 не зависят и могут идти параллельно другим исполнителем.

## 7. Формат модели `SPM2`

Код и точная раскладка байтов: `crates/sunpetal-data/src/spm2.rs` (докстринг модуля). Лежит в той же секции `MODL`, что и старый `SPM1`: запись секции опознаётся по первым четырём байтам, оба формата могут стоять рядом (`models::entries`, `models::unpack` — `SPM1`, `spm2::unpack` — `SPM2`).

Что в модели:

| Блок | Содержимое | Почему так |
|---|---|---|
| Заголовок | `unit` — множитель позиций (у всех 325 моделей PS2 `SceneScale` = 0,1) | позиции хранятся как в PS2, без пересчёта: сверка с эталоном `vtx.bin` побайтная |
| Привязка к DS (необязательна) | имя модели DS из словаря её файла (`no46_room_402r`), размер файла (0 — любой), номер меша или «все», матрица 3×4 «модель PS2 → пространство модели DS» | по У3.4 пачка опознаётся по модели, из файла которой игра её шлёт, не по ключу текстуры; имя уникально у 250 из 252 имён (259 файлов), повторы (`no82_light_house` в A81/A82, `ch_01_switchskin` в C093–C099) различает размер файла |
| Кости | родитель, стандартный номер PS2 (по нему ключи GIM), кость DS (для запасного пути Р-2), поза покоя: сдвиг и три угла (`T·Ry·Rz·Rx`) | один формат обслуживает оба пути анимации; модель из нескольких объектов PS2 склеивается в один список костей с несколькими корнями |
| Материалы | картинка (хэши данных и палитры, размер), проход 0–2, смешивание (сплошной, вырез, полупрозрачный, сложение, 255 — не известно), флаги (двусторонний, clamp s/t) | до 247 материалов на модель; проходы PS2 несут разную геометрию (проверено: у 14 из 15 моделей с двумя проходами общих вершин меньше 10 %), рисуются по порядку; смешивание заполнится после `[X-16]`, до того выводится из прохода |
| Вершины, 40 Б | позиция в осях своей кости, нормаль, цвет RGBA, uv, номер кости | привязка жёсткая, одна кость на вершину (F-11); слот 0–2 пакета PS2 при конвертации заменяется номером кости |
| Части и индексы | часть = материал + диапазон индексов; треугольники (полосы развёрнуты, обход исправлен) | части идут подряд без дыр — это проверяет разбор |

Разбор отклоняет: обрезанное и лишние байты, нечисла, родителя вне списка костей и петлю родителей, вершину без кости, часть без материала, неполные треугольники, дыры между частями, индекс за вершинами, проход больше 2.

Объём: в выгрузке 1,4 млн вершин (51 МБ по 36 Б), самая большая модель — 28 тыс. вершин. В `SPM2` это около 57 МБ до сжатия плюс индексы. Сжатие и квантование (нормаль в 3 байта, uv в 16 бит) — только если замер У2.5 покажет, что размер мешает.

Чего в формате нет намеренно: анимаций (отдельная секция, У2.3), самих картинок (секция `TEXS`, У2.4), света сцены (У6.4), волос GOM.
