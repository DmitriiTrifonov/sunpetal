# Инструменты отладки (`sunpetal-debug`)

Для вычитки перевода: запускает игру без окна, отвечает JSON-строками на stdout и PNG-файлами. Ход работ и устройство движка: `DEBUG-TOOLS-PLAN.md`. Всё под cargo-фичей `debug-tools`, обычная сборка и `sunpetal-headless` не затронуты.

## Сборка и запуск

```sh
cargo build --release -p sunpetal-runtime --features debug-tools --bin sunpetal-debug
ROM=путь/к/игре.nds                 # европейский ром (YHNP) или перевод на нём же
cp save.sav /tmp/work.sav           # --save изменяют: работать на копии
target/release/sunpetal-debug "$ROM" --save /tmp/work.sav --goto C18_01 --autoplay \
    --dialogue-log out/log.jsonl --out out/png --state
```

Сохранение: 64 КиБ EEPROM, нужен слот, где запросы уже открыты (путь к началу главы идёт через меню «Request»). Без `--save` берётся новое сохранение: запросов в нём нет, `--goto` не дойдёт.

Игра идёт по кадрам, время виртуальное: те же флаги дают те же кадры. Строки stderr (звук, VRAM) — журнал рантайма, на stdout только JSON.

## Флаги

| Флаг | Что делает |
|---|---|
| `--dialogue-log FILE` | по строке JSON на каждое открытое окно реплики (схема ниже), запись сразу на диск |
| `--goto Cnn_yy[,Cnn_yy…]`, `--scenes FILE` | список сцен в одном процессе (ниже, «Несколько сцен»). `--goto Cnn_yy` одна: | `Cnn_01`: начало главы `nn` через меню «Request» (запрос N = глава N). Любая другая: сначала начало главы и вступление (A до первой свободной ходьбы), потом шаг истории и двери (ниже), игра сама запускает сцену, когда герой на месте её события |
| `--chapter N` | то же, что `--goto CNN_01` |
| `--autoplay` | A после каждой реплики до конца сцены, лимит `--max-lines` (200) |
| `--frame-delay N` | кадров паузы после открытия реплики перед снимком окна (120) |
| `--out DIR` | снимок окна реплики в `DIR/<сцена>_<ID>.png` (полоса 256 × 56 нижней части верхнего экрана) |
| `--shot FILE` | оба экрана PNG в конце |
| `--state` | в конце строка `{"state": последняя реплика, "frame", "map" (карта героя), "value0" (шаг истории), "stop"}` |
| `--repl` | команды со stdin, ответ строкой JSON (ниже) |
| `--set valueN=V` | записать числовое значение истории `N` как `SETVALUE N V` (0 — шаг главы). `--set value0=V` заменяет шаг, который `--goto` берёт из события сцены |
| `--text-dir DIR` | реплики сцен берутся из `.s` под `DIR` (строки, начинающиеся с `//`, — заметки переводчика и в текст не входят, пустые строки по краям тоже; папка одного языка; если у сцены несколько файлов, берётся лежащий в папке `ue`, иначе первый по имени): когда игра загрузила сцену, её тексты кладутся поверх игровых (память из кучи игры, указатель команды переставляется) |
| `--watch` | с `--text-dir`: время файла проверяется дважды в секунду игрового времени, изменённый файл кладётся заново (в лог пишется новая строка реплики; окно, которое уже нарисовано, обновится при следующем показе реплики) |


Конец автопрокрутки печатает `"stop"`: `max_lines`, `scene_end` (сцена сменилась) или `stalled` (десять секунд A без новой реплики: головоломка, ходьба или ролик; либо шесть реплик подряд, которые в этой сцене уже показывались: сцена ждёт события или таймера, который A не проходит — C04_03, C04_07; снимок на остановке — `--shot`).

## Готовые команды для глав 4 и 18

```sh
ROM=путь/к/игре.nds; cp save.sav /tmp/w.sav   # сохранение с открытыми запросами
D=target/release/sunpetal-debug
# глава 18, сцена C18_01 (20 реплик): начало запроса R-18, A до конца
$D "$ROM" --save /tmp/w.sav --goto C18_01 --autoplay --out out/png --dialogue-log out/c18.jsonl --text-dir patched/Chapter/Pack/C18
# глава 4, сцена C04_16 (19 реплик): шаг 60, двери 46→45→36→30→34→27, место события (сама)
$D "$ROM" --save /tmp/w.sav --goto C04_16 --autoplay --out out/png --dialogue-log out/c04.jsonl --text-dir patched/Chapter/Pack/C04
python3 tools/debug/check_log.py out/c04.jsonl --scene C04_16 --s patched/Chapter/Pack/C04/ue/C04_16.s --table accept-scenes.md
```

Шаг истории можно задать самому: `--set value0=N` (он заменит шаг из события сцены).

## Несколько сцен за один запуск

`--goto C04_01,C04_03,C04_04` или `--scenes list.txt` (по сцене в строке, `#` начинает заметку): сцены идут по порядку в одном процессе. Первая — от запроса, следующая той же главы — оттуда, где игра осталась (без меню «Request» и вступления: `settle` доигрывает сцену до свободной ходьбы, A раз в секунду, не дольше 40 с; не вышло или сцена не запустилась так, как запустилась бы одна, — остаток списка идёт новым запуском программы с теми же аргументами: игра грузится заново из сохранения, как при одной сцене; журнал дописывается, вступление главы в него второй раз не пишется), другая глава — так же заново. Журнал реплик и `--out` общие, в записях журнала `scene` свой. На каждую сцену строка JSON на stdout: `{"scene", "status", "stop", "lines", "state", "frame", "map", "value0", "error"}`; `status`: `ok` (сцена кончилась или показано `--max-lines`), `stalled` (ждёт ходьбу, событие или таймер), `no_event` (событие главы её не запускает), `not_started` (герой на месте, игра сцену не начала; текст в `error`). С `--autoplay` каждая сцена проигрывается, без него только запускается. Одна сцена в `--goto` работает как раньше.

Проверка: десять сцен главы 4 (`C04_01,03,04,06,08,09,10,11,12,14` и `C04_33`) одним вызовом, на сохранении 100 %: те же реплики, что по одной (18, 8, 39, 41, 4, 10, 8, 10, 3, 11), `stalled` у всех, C04_33 — `no_event`; ~6 мин против ~12 мин по одной (после C04_09, C04_12 игра не выходит на свободную ходьбу, и остаток идёт новым запуском).

## Схема строки лога реплик

```json
{"frame":6635,"scene":"C18_01","id":"01001","face":5,"text":"…\n…","lines":2,"widths":[117,100],"overflow":false}
```

- `frame` — кадр игры, на котором окно открылось;
- `scene` — `Cnn_yy`, по последнему прочитанному с картриджа скрипту;
- `id` — ID реплики как в `.s` (пять цифр), из памяти игры;
- `face` — номер лица из ближайшей раньше команды `SETFACE2` в порядке скрипта (при ветвлениях может отличаться от порядка показа);
- `text` — финальный текст, `\n` между строками;
- `lines`, `widths` — число строк и ширина каждой в px по шрифту игры: сумма (продвижение + 1) по всем буквам, кроме последней, у последней ширина глифа. Совпадает с `accept-scenes.md` на C18_01 до пикселя;
- `overflow` — больше 3 строк или шире 194 px;
- `portrait` — `"left"`, если в окне портрет (слово игры `[020759EC + 0x34]`, его ставит `SETFACE2` с лицом, не −1), иначе `null`. `"right"` движок не выдаёт: см. «Сторона портрета» ниже;
- `text_x0`, `text_x1` — столбцы экрана (из 256), где текст начинается (58) и где игра его обрезает (243, не включая): проверка `text_x0 + max(widths) <= text_x1`.

`id`, `face` и `scene` бывают `null`, если игра их не показала (реплика не из `.s`).

## Сторона портрета и границы текста

Движок рекомпа (оригинальный европейский ром) рисует окно диалога в одной раскладке: портрет слева (его рамка — красная линия на x = 48), текст с x = 58. Ни один параметр `SETFACE2` (лицо; второе число; третье 0/1/2) сторону не меняет: код обработчика (`02049178`) читает лицо, режим «дрожь» портрета (третье число 1 — генератор случайных смещений `0205641C`) и флаг «есть портрет» (третье число 2 или лицо −1 — портрета нет). Сторону он не задаёт. Поэтому `portrait` в логе — `"left"` или `null`.

Границы измерены на движке: в сцену C02_01 подставлена строка из `W` известной ширины (`--text-dir`), по кадру смотрели крайний столбец чернил. Начало 58 при любой ширине; строка 175 px кончается на x = 232 (= 58 + 175 − 1), 186 px — на 242 (на единицу короче ожидаемых 243), 197 px обрезана на 242. Значит, видимы столбцы до 242 включительно, `text_x1 = 243`, самая длинная целиком видная строка ≈ 185 px. Лимит 194 в `overflow` — прежний, он не про окно.

Без портрета (`portrait: null`, лицо −1) текст остаётся с x = 58 (проверено: слово `[020759EC + 0x34]` = 0 убирает портрет и рамку, текст не двигается).

**Откуда «правый» портрет на старых кадрах melonDS** (`fsar-ru/dumps/emu/u4, u5, z3…g13`: рамка на x ≈ 207, текст с x = 10). Из всех 3644 PNG в `dumps/` такая раскладка только на 23 кадрах в `dumps/emu/` за 17–18 октября; на всех кадрах `dumps/emu/walk/r0…r18` (сборка gfx16 и позже: 21–45 кадров на главу) рамка на x = 48, как в рекомпе. C00_01 в рекомпе: 12 реплик подряд слева, `01001` в том числе. Параметра стороны в коде, который я разобрал (`SETFACE2`, окно), нет и ни в одном из прогонов она не появилась; причина, судя по всему, в тех старых сборках рома (правка графики окна или кода в самой сборке перевода), а не в сцене, лице или камере. Чтобы закрыть вопрос, нужен ром, на котором снят `u4.png`: на нём этим же инструментом видно, чьи это данные.

**Что решать с лимитом.** В оригинальной раскладке обрезка с 243, лимит 188 px оставляет запас; единой «широкой» раскладки в движке нет, 194 не добавлять.

## Выбор ответа

В игре нет выбора ответа в диалогах: тег `<CHOICE>` (код 25 в таблице тегов, обработчик `0204824C` — заглушка) не встречается ни в одном скрипте (`Chapter/Pack/*/*.txt`, проверено по всем сценам). Ветвления делают `JUMP`/`CHANGEBYVALUE` по значениям истории, без вопроса игроку. Поэтому остановки «на выборе» нет и опции логировать нечего. Остановка `stalled` значит свободную ходьбу, головоломку или ролик; по `map` и `value0` в `--state` видно, где игра встала.

## Как работает `--goto` для сцены в свободной ходьбе

Всё через логику самой игры, без подмены текста и записи в её структуры сцены:
1. Событие сцены берётся из `Chapter/Pack/Cnn/Cnn.EVN` в ROM (запись по 104 байта: имя, карта, место, нужное значение шага).
2. Игра доходит до первой свободной ходьбы: запрос N, A по вступлению.
3. `SETVALUE 0 <шаг из события>`: обработчик команды скрипта самой игры (адрес `0204859D`), вызывается из хоста на входе в её цикл событий.
4. Двери: события `Ann_yy` главы, чей скрипт делает `CHANGEMAP`, образуют граф карт; кратчайший путь от карты героя до карты события. На каждую дверь: герой ставится на её место (позиция в записи героя `+0x18`), A, ожидание карты героя (`+0x0C`), 4 с на загрузку.
5. Остальные события сцен главы «гасятся» (первый байт имени в таблице событий игры = 0, двери остаются): на одном месте и шаге игра запускает первое подходящее событие, а условие «шаг ≥ N» у многих сцен (флаги `0xd`) держится и дальше. Пример: на шаге 30 стоящий там же C04_06 (≥ 20, одноразовое) перехватывал C04_08. Это только в памяти сеанса.
6. Герой ставится на место события; игра сама видит его и запускает сцену, A каждые 90 кадров (сцены «по разговору» ждут A).

Лог реплик: если окно ещё открыто, а память его буфера игра заняла под другое (тот же указатель и ID, другие байты), новая запись не пишется. Ошибка `sunpetal-debug` идёт и в stderr, и строкой `{"error": …}` в stdout (`--goto` по несуществующей сцене: `no event starts it`, код 1).

Если сцену не удалось запустить, `--goto` останавливается и пишет, на какой двери или карте. Тогда нужен ещё шаг истории (`--set value0=N`) или другая дверь.

Условия события в игре (цикл `02023745`, слово флагов `+0x38` записи): бит 2 (`0x4`) — шаг ≥ `value_min`; бит 5 (`0x20`) — шаг в `low..high`; бит 0 (`0x1`), 10, 12 — одноразовое (слово `+0x30`); героя должно быть в пределах ±4000 (1/4096) по всем трём осям; запуск требует бита 3 (`0x8`, по A), 4 (`0x10`) или 7 (`0x80`, сразу). События без этих битов (C04_02, флаги `0x45`) отсюда не стартуют: сцена идёт цепочкой от предыдущей, `--goto` её не достанет.

Глава 4 на сохранении 100 %: запускаются сцены, проверенные здесь: 03, 04, 06–12, 14, 15, 17–29 (01, 05, 13, 16, 30, 31 запускались и раньше); не запускается C04_02. C04_33 в главе нет (события до C04_31, затем `C04_NEW01…03`, `C04_LIST`).

Время: C04_16 ≈ 70 с (вступление главы и четыре двери).

## REPL

`--repl` читает команды, по одной в строке; ответ — строка `{"ok":true,"vblank":N,…}` или `{"error":"…"}`:

`skip [FRAMES]` (как F7 в приложении: без нажатий, до команды `WAIT` скрипта или до свободной ходьбы; ответ `stopped`: waits/idle/limit) | `request N` | `setvalue I V` | `value I` | `teleport X Y Z` | `changemap MAP X Y Z` (приложение обработчика: действует только внутри идущего скрипта) | `run N` | `press KEYS [FRAMES]` | `tap X Y [FRAMES]` | `shot FILE` | `log FILE|off` | `advance [FRAMES]` | `walk N [FRAMES]` | `shown` | `quit`.

Кнопки: `A B SELECT START RIGHT LEFT UP DOWN R L X Y`, через `+`. `peek` и `dump` читают и регистры, палитры, VRAM, OAM (`04…07`), как их видит ARM9. Остальные команды (`peek`, `find`, `findhex`, `slots`, `calls`, `callsarg`, `callsstr`) — разведка движка, не часть схемы.

## Тесты

Без рома: `cargo test -p sunpetal-runtime --features debug-tools --lib` (разбор тегов `.txt`, строк `.s`, LZ10, записей `.EVN`, маршрута по дверям, ширина строки на синтетике).
С ромом (пропускаются без переменных): `SUNPETAL_ROM=… SUNPETAL_SAVE=… cargo test --release -p sunpetal-runtime --features debug-tools --test debug_goto --test debug_autoplay --test debug_event` (~3 мин).

## Предложение: пять команд MCP

Поверх `Session`, один долгоживущий процесс без повторного прохода от запуска: `goto(scene[, value0])`, `advance(n)` (A до новой реплики, вернуть её строку лога), `screenshot(region)`, `dialogue_log(from)` (реплики с кадра), `reload_text(dir)` (после появления подмены текста).

## Заметка: запросы, кратные трём без одного

Третья строка списка (R-02, R-05, …) стоит правее первых двух; касание в `x = 150` её не задевало, и `--goto Cnn_01` не стартовал для глав 2, 5, 8, 11, 14, 17 (ответ «the game never read Cnn_01»). Касание теперь в `x = 230` (полоса идёт до края экрана). Допущение «запрос N = глава N» подтверждено на 2, 3, 4, 5, 8, 11, 14, 17, 18 (первая реплика читается из `Cnn_01`).
